# 面向角色的JSON战斗策略编辑器

一个**离线单文件网页**，用来可视化编辑 BetterGI 的 JSON 战斗策略（`User\AutoFight\*.json`）。
目标：编辑者只关心「哪个角色、什么动作、什么条件下做」，**编号（index）与判定优先级（priority）由网页自动推导**。

> 名字里的「面向角色」是刻意加的定语：这个编辑器为了方便**以角色为单位**编辑战斗动作、并简化动作优先级分配，
> 采用了**固定的 index 分配逻辑**（动作类型 + 元素 + 角色编号 + 同类型序号，全部由网页算出来），
> 不是那种每一部分内容都能自由编辑的 JSON 策略编辑器。要手写任意编号/任意结构请直接改 JSON。

## 1. 怎么用

1. 双击打开 `面向角色的JSON战斗策略编辑器.html`（Chrome / Edge 均可；无需服务器、无需联网）。
2. 在「策略信息」页填名称/作者/版本/描述，需要时点「一键填写「战斗配置设置流程」」。
3. 在「动作编辑」页左侧选角色 → 选动作类型 → 点「+ 添加新动作」→ 在卡片里填名称与指令、配条件（需要写说明时就展开卡片里的「注释」）。
4. 在「优先级预览」页核对展开后的判定顺序（可选：设 4 人队伍做模拟过滤）。
5. 回「策略信息」页点「导出 JSON 策略」，把文件放进 BetterGI 的 `User\AutoFight\` 目录。

编辑内容会自动存成浏览器本地草稿（按**策略名称 + 版本**归档，最多 30 份），可随时用「本地草稿…」切回。
「策略名称 / 版本」这两项的改动不会边打字边保存，而是等你**改完**时一次性写进草稿。判定「改完」的方式是
**你把光标移到了别的输入框、点了别的按钮 / 下拉，或者切了页**（改其他内容也会立刻落盘）；
**不再用「离开输入框（失焦 / change / 组字结束）」判断** —— 中文输入法（例如微软拼音）组字期间这些事件都可能
在还没输完的时候触发，会把只输了一半的名称当成改完写进草稿。这样草稿列表里不会出现一堆名称只改到一半的条目；
改其他内容仍是原来的即时保存。

## 2. 编号规则（index）

每条动作的 index 由 5 位十进制数字构成，导出时省略首位非 0 数字之前的 0：

```
[动作类型 1位][元素类型 1位][角色编号 2位][同类型第 N 条 1位]
  0~9            0~7          01~99        1~9（0 为插入位，不用于动作）
```

* 动作类型（第 1 位）——按「默认状态下应有的施放顺序」划分：

  | 数字 | 类型 | 数字 | 类型 |
  |---|---|---|---|
  | 0 | 战斗检查与标记（**只用于「当前角色」**，编号退化为 1 位：`1`~`9`） | 5 | 爆发 |
  | 1 | 开盾 | 6 | 前台长轴输出 |
  | 2 | 先手或挂元素 | 7 | 回血或低收益技能 |
  | 3 | 后台输出 | 8 | 纯挂元素普攻 |
  | 4 | 辅助 | 9 | 兜底普攻/等待 |

  每种类型的详细含义见网页「策略信息 / 导入导出」页 →「关于编号规则」。

* 元素类型（第 2 位）——按**元素反应的先后手顺序**分配：`0` 元素未定/当前角色，`1` 冰，`2` 火，`3` 水，`4` 雷，`5` 风，`6` 岩，`7` 草。
* 角色编号（第 3~4 位）：同元素内按 BetterGI 内置角色表（`combat_avatar.json`）次序从 `01` 开始；
  `00` 留给 `character` 字段为空的「当前角色」。
  元素 0 下：`00` 当前角色、`01` 旅行者、`02` 奇偶·男性、`03` 奇偶·女性
  （旅行者/荧/空 是同一角色的两个性别，只保留标准名「旅行者」；`未知角色` 是 BetterGI 的兜底名，不作为可选项）。
  这一段的角色（旅行者、奇偶·男性/女性）不是“没有元素”，而是**玩家可以统一选择 7 种元素中的一种**，
  BetterGI 无法识别其当前元素，所以归类为「元素未定」。
* 第 5 位：**同一角色 × 同一动作类型**的序号，从 1 开始，**最多 9 条**；`0` 是预留给「其他触发条件」的
  priority 插入位，**动作尾数不可选 0**。

示例：`33011` = 后台输出 · 水元素 · 芭芭拉(01) · 第 1 条；`14041` = 开盾 · 雷元素 · 菲谢尔(04) · 第 1 条；`1` = 战斗检查与标记第 1 条。

> 元素号换过一次：早期版本是「1 水 / 3 冰」，现在按元素反应先后手改成「1 冰 / 3 水」。
> 导入旧策略时，只要**尾数与角色编号都对得上、只有元素位不同**，就会自动按角色所属元素改写元素位
> （尾数顺序保持不变，条件里 `since(N)` / `count(N,…)` / `last-exec(…,N)` 的数字引用同步改写），
> 不需要整份重排编号。

## 3. priority 推导

「其他触发条件」里不直接填数字，而是选「优先于 / 次于」+（动作类型 必选）+（元素 可选）+（角色 可选）：

* **优先于某段** → 取该段**最小值**；**次于某段** → 取该段**最大值 + 1**；该段当前没有动作时直接取段边界。
* 段按十进制错位定位（与 index 结构一致）：`[类型]` → `[类型][元素]` → `[类型][元素][角色2位]`。
  例：优先于开盾 = `10000`；优先于水元素辅助 = `43000`；次于水元素辅助 = `44000`；次于整个类型 9 = `100000`。
* 动作类型 0（战斗检查与标记）是一整段，段边界 `0 ~ 9999`，不能再按元素/角色细分。
* 「判定顺序」默认「次于」；选角色会自动锁定其元素；类型选 0 时元素/角色不可选。
* **导入或载入草稿时，priority 数值会自动还原成「优先于 / 次于某类动作」的选择**：
  数值等于哪个段的边界，就还原成对应的那一段；同一个数值既能解释成「优先于某段」又能解释成「次于上一段」时
  （例如 `10000` = 优先于开盾 = 次于战斗检查与标记、`43000` = 优先于水元素辅助 = 次于火元素辅助），**一律优先取「次于」**；
  判定范围也会尽量还原到最具体的一级（角色 → 元素 → 类型）。实在对不上任何段边界的数值（例如 `30`、`43`）保持原值，
  并在校验面板提示需要手工选择判定范围或点「按选择重算 priority」。
* 导入时如果某个 priority 的**尾数不是 0**，会弹窗询问：**修正后导入**（改成所在段的边界值，判定顺序按“次于”）或**放弃导入**；
  同一 priority 同时存在“优先于”和“次于”能命中时，**优先保留“次于”**。
* ⚠️ 元素号换过一次（原来是「1 水 / 3 冰」，现在是「1 冰 / 3 水」）。priority 的**数值不会被改写**，
  所以旧策略里靠数值表达出来的“哪一段”在新规则下可能指向别的元素 —— 导入后建议在
  「其他触发条件」里核对一下判定范围再导出。

## 4. 页面与功能

### 策略信息 / 导入导出
* 策略名称（`name`，占位提示：例如：全角色通用（实验性））、作者（`author`）、版本（`version`，写在 `author` 下面、
  `description` 上面）、描述（`description`，写在 `version` 下方）、战斗前动作（`preActions`）。
* **`version` 的两个用途**：① 版本元数据（BetterGI 运行时不读取它，和 `description` 一样只是给人看的）；
  ② 本地草稿的归档条件之一 —— 草稿按**策略名称 + 版本**归档，二者有其一不同就是两份不同的草稿，
  配合「本地草稿…」就能在不丢旧版本的前提下改出新版本。
  新建策略、或导入没有 `version` 的策略时，「版本」默认为空；导出时 `version` 为空会**省略**这个字段
  （再次导入时「版本」仍为空，内容不会变）。
* `config` 以「设置」呈现：**当前版本下设置不提供编辑**，因为对应的 `config` 字段在 BetterGI 运行时暂不读取；
  从本编辑器导出的 `config` 固定为空对象 `{}`（为将来 BetterGI 开始读取该字段预留了位置）。
* 战斗前动作提供角色下拉（上方搜索框可按角色名/编号过滤上百个角色）+ 指令编辑器；
  提示「角色名按第一个空格切分，指令串内不能有空格」。
* 「快捷插入指令」在这一项下面**就地展开**（不再弹窗），避免打断连续输入；点词条 → 填参数 → 选「插入光标位置 / 插入末尾 / 替换全部」。
  插入完成后**光标停在刚插入的指令后面**（面板重建不会再把光标丢回开头），方便接着输入或连续插入。
  参数留空时会自动省略括号与逗号（例如「连续普攻」清空秒数就插入 `attack`）。
  按键图选完键会把选择的键写回参数框（不会被默认值覆盖回去）。
  指令词表里与按键相关的词条有「点按按键」`keypress(键)`、「持续按下按键」`keydown(键)`、「松开按键」`keyup(键)`、
  「长按后松开按键」`keydown(键),wait(秒数),keyup(键)`（键由按键图选择、两个指令共用同一个参数，秒数为数值输入）。
* **手输指令时会实时校验**：输入框下面立刻列出未知指令/参数错误/中文括号等问题，右侧校验面板与顶部徽标同步刷新。
* 导入：先做与 BetterGI 一致的解析期校验 → 无法加载的直接拒绝；`condition` 写成裸字符串的会**弹窗询问后自动修复**；
  **动作节点里既不能识别、也不支持编辑的字段（例如正式版 BGI 里不存在的 `redArrowAim`）会被忽略，但不会静默**
  —— 导入弹窗的「⑨ 既不能识别、也不支持编辑的字段」一节会逐条列出（BetterGI 对多余字段本来就是静默忽略的，
  本编辑器同样忽略它们，只是明确告诉你；这些字段不会写进草稿与导出的 JSON，需要保留请自行备份原文件）；
  index 不符合本规则的弹窗选择**取消导入**或**重排编号后导入**（同时改写条件里 `since(N)/count(N,…)/last-exec(…,N)` 的数字引用，
  并按指令内容与 `ensureCast` 推定动作类型：有 e 类指令且勾了 ensureCast → 开盾；没勾 → 辅助；只有 q → 爆发；
  只有普攻/重击 → 纯挂元素普攻；都没有 → 兜底普攻/等待；类型满了顺延到编号更大的类型，9 之后回到 1，顺延 8 次都满则删除该动作）；
  如果只有**元素位**与角色不符（旧编号规则或手写错误），则直接按角色所属元素修正元素位，**尾数顺序不变**。
* 导出：先整体校验，有错误直接拒绝并列出原因。
* **合并 JSON 策略**（`合并 JSON 策略…` 按钮）：把另一份策略**有选择地**并进当前正在编辑的策略，
  以当前策略为基础，只在两份策略有差异的地方询问你怎么取舍；详细规则见下面「合并 JSON 策略的规则」。
  入口与「导入」一样支持**选择文件 / 粘贴 JSON 文本**，完成后弹窗汇总这次合并做了什么。

### 合并 JSON 策略的规则

前提（规则 1）：**当前策略必须没有阻止导出的错误**；**被导入的策略必须先能正常导入本编辑器**：

* 无法被 BetterGI 加载的（JSON 结构错误、`condition` 是裸字符串、动作名不合法、动作数超限…）→ **按错误原因拒绝**；
* 本身能跑，但**编号 / priority 等方面需要先调整**才能导入本编辑器的（index 不符合规则、index 重复、
  元素位需要按角色修正、动作类型顺延、同角色同类型超过 9 条、`morePriorities.priority` 尾数不为 0、
  角色不在角色表中、动作名重复）→ 提示 **「该策略应先单独导入并编辑后，才可以与其他策略合并」**并拒绝；
* 只有「既不能识别也不支持编辑的字段」与「队友条件结构不常规」这类提示不阻止合并（会在汇总里一并列出）。

`info` 的合并（规则 2）：以当前策略的 `info` 为基础逐字段比对 `name / author / version / description / config / preActions`：

| 当前字段 | 被导入字段 | 结果 |
|---|---|---|
| 空 | 有内容 | 采用**被导入**的内容 |
| 空 | 空 | 留空 |
| 有内容 | 空 / 与当前相同 | 保留**当前**的内容 |
| 有内容 | 有内容且不同 | **弹窗逐个字段询问**：使用当前版本 / 使用导入版本 / 全部使用当前版本（后续不再询问） |

`actions` 的合并（规则 3~5）：以当前策略的 `actions` 为基础，用 `name` 与被导入策略的动作逐个配对：

* **没有同名动作** → 该节点直接导入，**按它原来的动作种类重新分配 index**（角色不变，取该角色该类型下第一个空闲尾数）；
  该类型已有 9 条时**顺延到编号更大的动作类型**，类型 9 满了回到类型 2，再依次往后（`9 → 2 → 3 → … → 8`）；
  9 种类型都满了则**拒绝合并**并说明是哪个动作（先删掉一些再合并）。
* **有同名动作** → 比对**除 index 以外**的全部字段（`character / action / ensureCast / condition / tags / morePriorities`）。
  比对条件时会把两份策略里「入参为动作」的条件函数（`since` / `count` / `last-exec`）的 **index 数值先换算成各自策略里的动作名**，
  所以「`since(43111)`」与「`since(芙芙e)`」指向同一个动作时会被判为相同。
  * 完全相同 → 直接保留当前的动作节点（比对时的换算**不会写回**，入参原来怎么写就还是怎么写）；
  * 有不同 → 弹窗展示不同之处，逐个动作询问：
    * **保留当前版本**：当前节点完全不动；
    * **使用导入版本替换**：除 `index` 外全部换成导入版本（`index` 仍用当前数值；若角色不同，`index` 的元素 / 角色位
      会跟着角色改写，当前策略里指向该 index 的引用同步改写）。条件里「入参为动作」的 index 会按
      「被导入策略里该 index 指向的动作名 → 本策略里同名动作的 index」换算；那个名字只在被导入策略里出现时，
      用导入后为它重新分配的 index。**这条会不可逆地覆盖当前内容，因此不提供「全部替换」的一键选择**；
    * **导入的版本改名后保留**：当前节点不动，导入的这条在**原名后加数字**（`芙芙e` → `芙芙e2`、`芙芙e3`…）
      作为新动作导入，index 按「没有同名动作」的方式重新分配。
    * 另外提供**「全部保留当前版本」**与**「全部改名后保留」**两个一键选择（后续同名动作不再逐个询问）。
* 当前策略里**没有同名动作与之配对的**动作节点按原样保留不变。
* 「自动排除」记的是动作 id，合并时按**动作名**映射成本策略里同名动作的 id；无法换算的 index 引用会原样保留，
  并在合并汇总里逐条提醒（合并后仍会走一次完整校验，不会悄悄产出坏条件）。

### 动作编辑
* 左侧角色列表：按「元素号 + 角色编号」排序（= 动作检索次序），显示每人已设动作数（有动作时用正常文字色，没有动作用灰色「无」）、星级；
  支持搜索（可按角色名/编号，**中文输入法组字期间不会重建列表**）、按元素筛选、按星级筛选（按星级筛选时隐藏未标注星级的角色）、
  按「有无动作」筛选、以及设满 4 人后的「只看当前队伍」。切换角色时列表滚动位置保持不变。
  首项是特殊条目「当前角色」，承载 `character` 为空的通用动作；「元素未定/当前角色」段里放当前角色、旅行者、奇偶·男性/女性。
* 动作卡片（按 index 升序排列，卡片内不再用子页签，改成 4 个可折叠区块，展开状态会被记住）：
  三个区块的标题旁都会带上**语句预览**（与「触发条件」的写法一致，空值时有占位提示）：
  「动作指令」旁是动作指令字符串、「触发条件」旁是触发条件表达式、「队友条件」旁是队友条件表达式片段。
  预览最多显示 2 行（超长指令串会截断，避免把卡片标题撑得很高），完整内容展开区块就能看到。
  * **动作指令**（默认展开）：可手输，也可「快捷插入指令」就地展开按词条填参数后插入（**默认展开，插入后也不会收起**，方便连着插下一条）；
    「已输入指令的释义」**默认收起**，需要时自己展开。释义区显示逐条指令的中文释义、未知指令提示、以及每条指令是否会触发切人。
    手输时**实时刷新**错误/警告与释义表（不重建面板，所以不会打断输入法与光标）。插入按钮紧挨输入框，并提示“先在输入框里点一下、把光标放到想插入的位置”。
  * **动作类型 / 尾数 / 确保E技能（ensureCast）**：类型切换会给冲突/超限的原因提示；开盾类型默认勾选「确保E技能释放成功」；
    尾数 0 不可选（已预留给其他触发条件的优先级数值插入）。
    「编号（自动）」那一行**下面**还有一行注释，列出**哪些动作的条件表达式引用了本动作**
    （`since` / `count` / `last-exec` 的入参，写 index 数值或写动作名都算，会被实时刷新）：
    以**动作名称**展示，鼠标移上去提示该动作的 `index` 与「动作指令」；没有被引用时显示「没有被其他动作的条件引用」。
  * **触发条件**（默认展开）：上面一个可直接输入的表达式框，下面「快捷添加条件」**就地展开**（不弹窗），
    提供条件函数与运算符的快捷输入（未列出的函数仍可手输）；再下面是释义与「运算顺序预览」（说明缩进与运算顺序的关系）。
    这里只写 in-party 以外的判断：写进 expression 的部分见下面的「expression 合并 / 拆分规则」。
  * **队友条件**：必要队友、排除队友、以及「自动排除」三部分，具体规则见下面两节。
    这些条件会写进该动作**所有** expression。
  * **其他触发条件**：可增删的列表，每条 = 触发条件（与基础触发条件同款的输入 + 快捷添加）+ 判定优先级（优先于/次于 × 类型/元素/角色），
    priority 自动算出并可一键重算；「添加其他触发条件」同样就地展开，里面手输或快捷拼出来的条件会在点「+ 添加这条其他触发条件」时带进新条目。
    表单里「判定顺序 / 动作类型 / 元素 / 角色」的选择会保留在页面上（重建面板也不会被重置），方便连着添加同类的条目。
  * **注释**（默认收起，排在「其他触发条件」下面）：一个文本框，内容保存在该动作节点的 `tags` 字段里，
    专门用来给动作写说明（例如「开场先手」「只有带盾队伍才用」）。BetterGI 的动作模型里没有 `tags`，
    但 Newtonsoft.Json 默认忽略未知属性（`MissingMemberHandling.Ignore`），所以它不会被读取、也不影响战斗；
    字段位置在 `index` 下面、`morePriorities` 上面；注释为空（或只有空白）时导出会省略 `tags`，
    再次导入时「注释」仍为空。有注释的动作卡片标题上会多一个 `注释` 标记；在空的注释输入框里打字时，
    这个标记与「注释」区块标题后的「已填写」会**立刻出现**（清空后一起消失），不需要收起再展开卡片。
* 「快捷添加条件」的用法：先选**条件函数**（选好后下面立刻出现参数输入区，「插入此片段」按钮同时变为可用）→
  然后二选一：**插入此片段到光标位置** / **插入此片段到末尾**；下面的「运算符与逻辑值」按钮则按
  「插入位置：光标位置 / 末尾」开关决定插入到哪里（默认光标位置；没有在条件输入框里点过光标时按末尾处理）。
  参数区的规则：
  * **出参是数值的条件函数**（t / since / count / last-check / e-cd / min / max 与两个组合）会带一个
    **比较下拉 + 数值输入框**：选「（空选）」或数值留空时只插入函数本身；选「大于 / 小于 / 等于」会插入 `> / < / =`;
    选「不大于 / 不小于 / 不等于」会在对应的比较外面套一层逻辑非，例如选「不小于」填 14 会插入 `! (t < 14)`。
  * **入参是动作**的条件函数（since / count 与两个组合）用**下拉选择动作**，写进表达式的是动作的 `index`；
    下拉上方还有「角色筛选 + 角色搜索框」，方便动作很多时快速定位；不选则写 `since()` 这类“本动作”。
    角色筛选里「（全部角色）」表示不筛选，「当前角色」表示只留 `character` 为空的那批动作（两者都能选、都能生效）。
  * **入参是角色**的条件函数（q-ready / e-ready / e-cd）保留角色下拉，并在旁边提供一个角色搜索框。
  * **两个组合函数**：「多个动作中是否有至少一个动作的距上次执行时间小于」= `min(since(参数1),since(参数2),…) < 参数a`；
    「多个动作中是否有至少一个动作执行超过指定次数」= `max(count(参数1,参数a,参数b),count(参数2,参数a,参数b),…) > 参数c`
    （每一项 count 的目标动作逐项选，起始/结束秒在下面统一填一次）。两者的**参数项数都是 1~9**。
  * 参数输入框旁边的「表达式快捷输入」按钮已移除（它只会往第一个参数框里插，容易出错）；需要拼算式请先插入函数片段再手改。
  * 「运算符与逻辑值」里有 `括号 ()`：插入后光标会停在括号中间。
* 工具栏「按规则重排编号」：按「角色 + 动作类型」重新分配尾数，并同步改写条件里的数字引用。

### expression 的合并 / 拆分规则（触发条件 ↔ 队友条件）

导出（合并）：

* **没有队友条件** → 触发条件原样写进 `condition.expression` / `morePriorities[].expression`（空就是空，恒真）。
* **有队友条件** → 一律写成 `(触发条件) && (队友条件)`；触发条件为空时用 `true` 占位，即 `(true) && (队友条件)`。
* 队友条件本身按三种结构组装（`&&` 连接，空的部分按下面的规则占位）：
  1. 只有必要队友：`(必要队友表达式)`；
  2. 还有排除队友：`(必要队友或true) && !(排除队友表达式或false)`；必要队友为空、又不需要写自动排除时，
     省略 `(true)` 占位，直接写 `!(排除队友表达式)`；
  3. 还有自动排除：`(必要队友或true) && !(排除队友表达式或false) && (true) && (自动排除表达式)`。
* **「排除队友」内部一律不取非，整段加括号后统一取非**：
  组合「或」（任一在场就排除）→ `!(in-party(甲) || in-party(乙))`；
  组合「与」（同时在场才排除）→ `!(in-party(甲) && in-party(乙))`。
  这样**用户选的「与 / 或」与表达式里出现的运算符完全一致**，并且和「必要队友」一样可以用「或」切分
  「角色组合」、靠运算优先级实现对多个「角色组合」的精准选择。界面上会就地显示这一组会生成的算式与最终片段。
  （`!(甲 || 乙)` 与 `!甲 && !乙` 在 BetterGI 的 `ConditionEvaluator` 里语义完全等价 —— `!` 是一元运算符、
  优先级高于 `&&` / `||`，括号内先整体求值；这里选前者的理由是运算符与界面选择一一对应、拆回来不会换写法。）
* 条件表达式的**规范化渲染**（「反解为条件行」「按规则重排编号」等会写回 JSON 的路径）会原样保留
  `!` / 负号作用于括号组时的括号：`!(t < 14)`、`!(in-party(甲) || in-party(乙))`、`-(t - 5)`
  往返（渲染 → 重新解析）之后语义不变。
* 结构 (3) 里那个 `(true)` 是恒等占位，同时充当**格式标记**：见到它就知道这份队友条件是本编辑器写的，
  里面的取非项才按「是否等于同角色某个动作的必要队友表达式」区分「自动排除」与「排除队友」。

导入 / 载入草稿（拆分）：以「队友条件必然包含 `in-party(...)`」为特征反推。

* 一条 expression 里，**从第一个含 in-party 的顶层 `&&` 片段开始**算队友条件；必要队友与排除队友都为空、
  只勾了自动排除时，队友条件里只有占位与自动排除项，这时从 `!(false)` 占位那里开始算。
  前面的（去掉末尾的 `true` 占位）算触发条件。
* 队友条件里：不取非的 in-party 组合 → 必要队友；取非项 → 排除队友或自动排除。
  - 取非项的形状决定「排除队友」怎么还原：新格式是**整段取非**（`!(甲 && 乙)`），把括号里的算式
    直接当作用户所选的写法（`&&` → 选「与」，`||` → 选「或」）；旧格式是**逐项取非**（`!甲 && !乙`），
    顶层 `&&` 只是多个组合的并列，每个片段内部按德摩根反推（`!甲 || !乙` → 用户选「与」）。
    两种形状的 in-party 链在 AST 里完全同形，靠解析器记录的「这一层括号包住了整个取非对象」区分。
  - 队友条件里出现过 `(true)` 格式标记时（本编辑器写出来的），取非段**末尾连续能对应到同角色其他动作
    「必要队友」表达式**的那些换算成那个动作的「自动排除」，前面的都按「排除队友」还原；
  - 没有该标记（旧版本 / 手写表达式）时，`(必要队友 && 取非段)` 与 `(必要队友) && (排除队友段)` 的操作数
    序列完全相同，无法区分 —— 这时**一律按「排除队友」还原**，绝不吞掉用户手选的排除队友。
  - 「自动排除其他「同一动作类型」动作的必要队友」的勾选状态：同类其他动作里设置了必要队友的那些，
    其必要队友都体现在本动作的排除条件里（勾了「自动排除」或手选的排除队友表达式恰好就是它）→ 勾上；
    一个设置必要队友的同类动作都没有 → 也勾上；只在其中一部分被覆盖时 → 不勾（用户是逐条手选的）。
* 同一个动作的 `condition.expression` 与各 `morePriorities` 的队友条件不一致时，按主条件（没有主条件就取第一条符合格式的其他触发条件）
  的队友条件导入，其余 expression 的队友条件部分会被替换，并在导入时**弹窗提醒**；
  只有其他触发条件带队友条件、主条件没带，或队友条件拆不出上面三种结构（这时整条按触发条件导入、不改内容）也会提醒。
  老版本（初版编辑器）导出的「必要队友 && 逐项取非的排除队友」结构仍按老办法处理，能拆就拆、拆不出就整条当触发条件导入。
* 不同动作之间的队友条件本来就允许不同（每个动作各自设置），这不算“不一致”，不会弹窗。

### 队友条件的组成规则

* **必要队友**：每项是 `in-party(角色)`，项与项之间可以逐个选「与 / 或」（`&&` / `||`），因此能写“甲与乙或丙”；
  也可以设置“未单独指定时”的默认运算符。**新增角色项前的运算符默认是「或」**。
* **排除队友**：输入方式和必要队友完全一样（可以有多个角色、逐项选「与 / 或」），表达的是**角色组合**：
  选「与」= 这些角色**同时在场**时才排除，选「或」= 其中**任意一个在场**就排除。
  表达式里整段加括号后统一取非，所以用户选的运算符与表达式里出现的运算符一致：
  组合「或」→ `!(in-party(甲) || in-party(乙))`；组合「与」→ `!(in-party(甲) && in-party(乙))`。
  默认的「或」正好等于旧版本“任意一个排除角色在场就排除本动作”的行为。
* **必要队友和排除队友都允许同一个角色重复出现**（多个角色组合里出现同一个角色很正常），
  角色选择弹窗里用「+ 添加」按钮重复添加、点标签上的 × 删除一个。
* **自动排除**：在被勾选的动作里，取其「必要队友」表达式、按文本去重（多个动作的必要队友相同时只算一次）、
  每项整体取非再用 `&&` 连起来：`!(甲动作必要队友) && !(乙动作必要队友) && …`。没设置必要队友的动作会被忽略。
* 三部分用 `&&` 连接；「必要队友」为空时补 `(true)`、「排除队友」为空时补 `!(false)`（取非后恒真），
  所以“空条件默认为真”与“整条 expression 为空视为真”的逻辑是自洽的。
* ⚠ 老版本表达式没有格式标记，「手选的排除队友」与「自动排除」在解析后同形，导入时一律按排除队友还原
  （条件语义不变，只是不再勾选那个动作）；重新导出一次就会带上标记，之后就能精确还原。
* ⚠ 手选的「排除队友」表达式恰好等于同角色另一个动作的「必要队友」时，导入只会把它还原成那个动作的
  「自动排除」勾选（表达式与语义完全相同，界面上表现为勾选而不是手写排除）。


### 优先级预览
* 按 BetterGI 的真实逻辑展开（每个动作 = 1 个主条目 + N 个其他条件条目）并按 priority 稳定排序，
  列出 `priority / index / 动作名 / 角色 / 触发条件`。
* 「动作触发条件」列显示的仍是**原始 expression 文本**（写法不变）；只有「入参为动作的条件函数」
  （`since` / `count` / `last-exec` 的动作参数）会带上鼠标悬停提示，提示该动作的 **index 与动作名**
  （有指令时一并显示指令），方便在长表达式里确认引用的是哪条动作。
  文本是按原文切片渲染的，所以除了多一个提示框，列里的内容与导出的 JSON 逐字一致。
* 「动作名」列的**动作名本身**也带悬停提示，提示该动作的**动作指令**内容（只提示指令，`index` 已经在旁边的列里）。
* 说明区用大白话解释「这张表是检查顺序、不是执行顺序」，并列出各动作类型段的边界值。
* 模拟队伍过滤：选满 4 人后，不在队伍中的角色动作会被剔除（与开战前过滤一致），该队伍也会被「只看当前队伍」复用。

## 5. 校验

编辑过程中持续校验，右侧「校验面板」列出错误与警告，**只提示、不阻止你继续编辑或切页**。

* **错误（阻止导出）**：动作名为空或非法（`true/false`、纯数字、与 14 个内置函数同名、含空白/标点/运算符）、动作名重复、角色名不在角色表、index 不符合编号规则或重复、同角色同类型超过 9 条、指令含未知方法/中文括号/中文逗号/`|`/`;`/`round`、参数个数或类型不对、条件语法错误/未知函数/引用了不存在的动作名、排除队友里含动作自己的角色、其他触发条件没选判定范围、`actions` 为空。
* **警告（不阻止）**：指定了角色的动作但第一条指令不会触发切人、`q` 后面没有 `ready`、勾了「确保E技能释放成功」但指令串里没有 `e`/`skill`/`keydown(e)`/`keypress(e)`、
  **`keydown(某按键)` 之后整条指令串里没有对同一个按键的 `keyup`**（按键名比较时忽略大小写与 `VK_` 前缀，例如 `keydown(e)` 配 `keyup(E)` 不算缺；这个按键可能会被一直按住，导致后续按键/普攻失灵）、
  通用动作里的 `q-ready`/`e-ready`/`onfield` 语义退化、引用了不存在的 index、重复的 priority、必要队友与排除队友里出现同一个角色（按「与/或」组合后不一定恒假，所以只提醒）、恒真/恒假的条目等。
* **隐式转换检查（数值 ↔ 布尔）**：单独一栏，**可点击标题展开/收起**（默认收起，标题上的徽标显示有几处），
  列出条件运算里“按位置推断的类型和期望类型不一致”的位置
  （例如把 `low-hp` 当数值参与加法、把 `count` 用在 `&&` 里、`t < since < count` 里第一个 `<` 的布尔结果又参与比较），并说明会发生哪种隐式转换。
  推断类型时会正确区分内置函数的出参（`t` / `since` / `count` / `last-check` / `e-cd` / `min` / `max` 是数值，
  `q-ready` / `e-ready` / `low-hp` / `onfield` / `in-party` / `battle-time` / `last-exec` 是布尔），
  所以 `t()>3`、`since(某动作)<3` 这类正常写法不会再被误报。
  正常校验不会给出这类警告，因为有时候隐式转换正是编辑者想要的效果。
  **用「快捷添加条件」插入片段后也会立刻重算**（以前会滞后一次，看到的是上一版表达式的结果）。
* 手输动作指令（战斗前动作、角色动作）时，除了本面板与顶部徽标实时刷新，输入框下面也会就地列出该指令串的问题；
  **动作卡片里的报错条、角标与条件摘要也会同步刷新**，改正后不会残留旧报错（以前要手动收起再展开才会消失）。
* 「其他触发条件」条目里那行提示（语法报错的红字 / 条件释义）也会跟着输入框实时刷新：
  手输把报错改掉之后，红字会一起消失，不会残留上一次的报错。
* 「快捷添加条件」的手输 + 快捷插入混用：模型是唯一事实来源，插入片段时会先把输入框里显示的内容写回模型，
  插入后重建面板时再按模型同步一次，所以「添加其他触发条件」里的条件输入框不会再出现“输的内容被清空”的现象。
* 「编辑时的检查要点」列出了最容易踩的几条坑（动作名命名规则、首指令切人、`q` 带 `ready`、ensureCast 必须有 e 类指令、条件入参出参类型）。

  例：`charge(...)` 这类长轴重击按规则会被推成「纯挂元素普攻(8)」，如果它其实是前台长轴输出，请手动改成类型 6。
* 元素号从「1 水 / 3 冰」改成了「1 冰 / 3 水」：旧策略导入时**元素位会自动按角色修正**，
  但 `morePriorities.priority` 的**数值不会自动改**（旧数值指向的段含义已变）。
  编辑器会把数值还原成「优先于/次于某类动作」的选择，但那是**按现在这套段定义**解释的，
  导入后请在「其他触发条件 → 编辑触发条件与优先级」里核对判定范围，必要时点「按选择重算 priority」。
* `morePriorities.priority` 允许负数与重复，也允许超过 100000（例如兜底动作常用 `priority: 100000`）；这些不参与编号规则校验。
* 队友条件的拆分只能识别「in-party 组合 + `!` / `&&` / `||` / `true`」这几种结构；
  手写的其它含 in-party 的条件（例如 `in-party(甲) && q-ready`）会整条按触发条件导入，并在导入时提示，不会丢内容。
* 合并策略时按 **`name` 全等**配对（空 name 也可以与空 name 配对）；条件里「入参为动作」的引用只在
  **数值入参**上做 index → 动作名 → 本策略 index 的换算，写成动作名的入参保持不变
  （所以指向「被改名保留」的那条动作时，按名称解析到的仍是当前策略里同名的动作）。
  被导入策略里**没有名字**的动作被引用时无法按名换算，数值会原样保留并在合并汇总里提醒。
* 网页只保证导出能被 BetterGI 正常加载；实际战斗效果仍取决于指令与条件本身的合理性。
